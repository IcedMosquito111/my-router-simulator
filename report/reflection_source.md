# 课程学习体会

标题：计算机与网络课程设计 - 课程学习体会
学号：1120241345
姓名：王文聪
日期：2026年9月18日
正文：

刚拿到"IPv4 分组转发与路由选择"这个课题时，我的第一反应是"无非是把课本上的 Dijkstra 写一遍"。真正做完整个系统之后，我最深的体会是：**把功能写出来只是开始，能证明它对、并且说清它有多快，才是真正的难点。** 这门课给我的训练，恰恰集中在后半句上。

在知识层面，我第一次把"转发"和"路由"这两件以前总是混在一起的事情分开理解了。路由是控制平面的事：每个路由器先通过 LSA 洪泛拿到全网一致的链路状态数据库，再各自用 Dijkstra 算出到其它节点的最短路径；转发是数据平面的事：拿着目的地址在路由表里做最长前缀匹配，找到下一跳和出接口，把分组交出去，同时把 TTL 减一。为了让链路两端恰好只有两个地址，我给每条链路分配了 /30（IPv6 是 /127）网段，给每个节点分配 /32 的回环地址——这时才真正明白 CIDR 与"最长前缀匹配"在工程上意味着什么，而不是只在试卷上算一算。另一个以前没有的意识是：**网络里不存在"瞬间一致"的状态**。我把 OSPF 的收敛拆成"生成 LSA → 洪泛 → 同步 LSDB → 各节点 Dijkstra"四步之后才明白，故障发生后每台路由器都是在用"自己掌握的那份拓扑"独立算路径，收敛是一个过程，而不是一个瞬间。

第二个收获是关于"怎么证明"。最初我对性能的描述是"很快"，写完测试之后变成了"穷举 50 个单节点故障与 75 条链路故障共 125 个样本，最慢 13.97 ms、平均 11.4 ms，相对 2000 ms 的指标余量不少于 143 倍"。差别不在于数字漂亮，而在于**穷举代替抽样**——课程要求是"发生单个节点或链路故障后不超过 2 秒"，只有把所有单点故障都跑一遍，这句话才是可证的事实。同样地，为了验证路由算得对，我在测试里另写了一份 Dijkstra 和 BFS，把系统生成的 4900 条路由与独立实现的最短路逐条比对，而不是用被测代码去验证被测代码；再加上"无黑洞路由、无过期路由、路由完备性"三条不变量，检查才真正有意义。

让我最难忘的是一次调试。在演示"链路故障 + 节点故障恢复"的场景时，我发现分组居然沿着一条已经断掉的链路"成功送达"了。顺着日志查下去，根因有两个：一是节点从故障恢复时，代码无条件把所有接口都置成 up，哪怕链路本身还断着；二是转发时只检查了下一跳节点在不在、没检查链路能不能用。这个 bug 让我第一次真切体会到"状态一致性"的代价——一个地方的状态不统一，整个仿真的结论就可能是假的。后来我把接口状态改成**派生量**：接口 up 当且仅当链路 up 且两端节点都 up，任何故障操作之后统一刷新；转发时每一跳都校验出接口、对端节点与链路，并把它固化成一条回归测试。类似的还有 TTL：我一开始想当然地在源节点也减了 1，导致 h 跳的路径要消耗 h 个 TTL，后来对照真实路由器的行为改成"只在中转路由器递减"，并用测试把"h 跳路径恰好需要 h 的初始 TTL"这件事锁死。

在性能上我也有了和"刷题"完全不同的一次经历。50 个节点时重算只要十几毫秒，看起来完全够用；但把节点数加到 400 时，单次重算涨到了 2321.6 ms，已经突破了 2 秒指标。分析后发现瓶颈有两处：Dijkstra 用线性扫描选点，整体复杂度偏高；以及每次往路由表写一条路由都要重新解析一遍前缀字符串，而这在同一条前缀上会重复成千上万次。改成最小堆加前缀解析缓存之后，400 节点降到 832.4 ms，50 节点也从 14.2 ms 降到 11.1 ms。为了避免"自说自话"，我用同一个测量脚本、同一个随机种子，把改动前后两个版本各跑 3 次取平均来做对比——这时我才明白，**做优化不难，难的是把对比做得可信**。

在协作与规范上，这门课也让我改变了习惯。以前写代码习惯一次提交一大坨，这次我用 Git 的功能分支开发、合并前自审，提交信息里写清楚"为什么改"而不只是"改了什么"；把随机拓扑固定种子、把拓扑导出成 JSON，保证同学和老师能复现同一个实验；把报告里的所有图表和数字都用脚本从实跑结果生成，避免"报告里的数字和代码里的实现对不上"。这些做法让我意识到，工程能力的一部分其实是**让别人能够相信并重复你的结果**。

最后想说，课程强调的"基线 + 提升"让我学会了先老老实实把需求全部满足，再主动去想"还能多做一点什么"：在完成了 IPv4 的基本要求之后，我补上了双栈 IPv6（节点和链路同时分配 IPv4/IPv6 地址，前端可以切换协议）、73 项自动化测试，以及上面提到的性能优化。成果简表里要求填写"具体方法名称和具体性能指标"，一开始觉得麻烦，后来发现正是这条要求逼着我把"我做了什么"讲成了"我用什么方法做到了什么程度"。

当然，这个系统还有明显的不足：它实现的是 OSPF 的核心机制而不是完整的协议时序，没有 Hello/Dead 定时器与邻居发现，因此报告里的毫秒级"收敛"是算法与实现的耗时，不能等同于真实网络的协议收敛时间；逐跳转发还在用真实的 sleep 模拟链路时延，多客户端也共用同一个模拟器实例。接下来如果有机会继续做，我希望把已经写好但尚未接入前端的 RIP 接进来，做 OSPF 与 RIP 在同一故障场景下的收敛对比，并把 LSA 的洪泛过程做成逐跳动画，让"路由交换"这件事被看得更清楚。

一句话总结这门课的收获：**从"能跑起来"到"能说清、能证明、能被复现"，是我在这门课里最大的一次转变。**
