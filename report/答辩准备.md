## 二、技术细节上的优点（每条都注明证据与可能追问）

1. **状态"单一真相"设计**：接口状态是派生量——接口 up ⇔ 链路 up 且两端节点 up，任何故障操作后统一刷新（`Topology.refresh_interface_states`）。
   - 证据：修复前实测"报文穿过已断链路却报告 delivered"，修复后同一场景路径绕行且不穿越死链路，并固化为回归测试。
   - 追问：为什么不让接口自己维护状态？→ 两处状态必然漂移，且故障恢复时无法区分"链路断"与"节点断"。
2. **转发每跳做三重可用性校验**（出接口 / 对端节点 / 链路），并校验下一跳位于出接口网段内（模拟 ARP 可达性检查）。
   - 追问：为什么不在算路时保证？→ 路由表可能是拓扑变化前的快照，转发平面必须自我保护。
3. **指标口径显式区分**：`convergence_ms`（纯路由重计算，需求判据）与 `total_ms`（含向所有客户端推送 N 张路由表）。
   - 追问：为什么不用墙钟？→ 墙钟受网络与渲染影响，不能证明算法效率；两个口径都给你。
4. **穷举而非抽样**：50 个单节点 + 75 条单链路故障全部实测，因此"任意单点故障都满足 2 秒"是可证事实。
5. **交叉验证而非自我验证**：测试里另写一份 Dijkstra/BFS，逐条比对 4900 条路由；再加三条不变量（无黑洞、无过期路由、路由完备性）。
6. **性能优化可归因**：最小堆 Dijkstra（原线性选点 O(N²)）+ 前缀解析缓存（同一条前缀一次同步中被解析 N 次）；
   - 对比方法同样讲究：用 `git worktree` 检出改动前版本，**同一脚本、同一种子、各重复 3 次**，排除拓扑差异的干扰。
7. **转发语义贴近真实路由器**：最长前缀匹配；本机投递（回环/自身接口地址）、直连投递（`direct`）、远端转发三类分支；TTL 只在中转路由器递减（源与目的不递减，h 跳路径最小初始 TTL = h），且用测试锁定。
8. **输入健壮性**：所有命令经 pydantic 校验（含协议与地址版本一致性），非法输入只返回结构化错误；实测修复前"非法命令会踢掉 WebSocket 连接"。
9. **并发正确性**：故障注入/恢复用 `asyncio.Lock` 串行化（并发注入同一故障只有 1 次生效）；广播 JSON 只序列化一次 + `asyncio.gather` 并发发送 + 单连接超时剔除。
10. **可复现与可观测**：固定随机种子；拓扑可导出/加载（有往返测试）；`/api/metrics` 直接给出指标是否满足；报告里所有数字由图/表脚本从实跑结果生成，不会与实现脱节。

## 三、不足清单（按答辩策略分三级）

### A. 已写进报告、应当主动说明（会显得你清楚边界）
1. **不是协议时序仿真**：实现的是 OSPF 的核心机制（LSA 生成 → 洪泛 → LSDB → Dijkstra），没有 Hello/Dead 定时器、报文格式、邻居发现、区域划分、DR/BDR、认证。因此毫秒级"收敛"是算法与实现耗时，**不能等同于真实网络的协议收敛时间**。
2. **LSA 洪泛是同步全网广播**：一次性把 LSA 复制到所有节点的 LSDB，没有逐跳传播过程与老化/冲突场景（序列号比较有，老化计时器没有）。
3. **逐跳转发用真实 `asyncio.sleep`** 模拟链路时延：8 跳路径会占用命令 8×delay ms，没有虚拟时钟与倍速。
4. **单例模拟器**：多客户端共享同一拓扑，无会话隔离、无鉴权、无持久化（重启即重置）。
5. **RIP 未接入前端**：算法实现并有测试（与 BFS 跳数一致），但只能通过 API/脚本演示，不能在界面做 OSPF/RIP 对比。
6. **最长前缀匹配是线性扫描 + 前缀缓存**，不是 Trie/LC-trie；路由条目多时查找是 O(路由数)。
7. **无 ECMP**：等价多路径只保留一条（Dijkstra 平局由堆顺序决定），也没有路由抖动抑制。
8. **没有 ICMP**：TTL 超时/不可达不会回送差错报文，只在日志与前端展示丢包原因。
9. **前端**：`vis-network` 走 CDN（离线演示会白屏）、单文件无构建、无端到端前端自动化测试（只有静态资源约定 + `node --check`）。
10. **无 CI**：73 项测试在本机运行，未接入流水线。

### B. 需要坦白承认（被问到不要硬撑）
- 没有做过系统性的并发/压力测试：只测了 5 客户端并发注入（235 ms / 5 次重算）；没有 50 并发、没有长时间稳定性测试。
- 没有用真实骨干网拓扑验证过，只有随机环形+弦边拓扑（另有可加载 JSON 的接口）。
- 性能结论是同一台机器上的相对值，没有做硬件标定；"余量 143 倍"依赖本机环境。
- 没有实现 IPv6 的 NDP/SLAAC/ICMPv6/扩展报头，也没有 IPv4↔IPv6 过渡机制（是双栈并行）。

## 四、预判问题与 30 秒回答

### 概念类
- **转发和路由的区别？** 路由是控制平面：LSA 洪泛得到一致的 LSDB，各自跑 Dijkstra 算出到各节点的最短路；转发是数据平面：拿目的地址做最长前缀匹配，找下一跳与出接口，TTL 减一。代码里分别对应 `routing/ospf.py` 与 `simulator._send_packet`。
- **为什么选 OSPF 而不是 RIP？** OSPF 用链路代价度量、每个节点有全网视图，收敛快且没有 15 跳限制；RIP 是距离向量，存在计数到无穷、收敛慢。两个都实现了（RIP 用跳数），主用 OSPF。
- **收敛为什么不是瞬间的？** 故障后每台路由器只能用"自己掌握的那份拓扑"独立算路，LSA 要传遍全网、LSDB 要一致，收敛是一个过程。

### 设计与实现类
- **最长前缀匹配你怎么实现的？** 路由表在写入时把前缀编译成 `ipaddress` 网络对象并缓存（前缀字符串只解析一次），查找时按"同地址族 + 前缀更长者胜"扫描匹配；规模更大时应换成 Trie。
- **TTL 怎么处理？** 只在中转路由器递减，源节点是发送方、目的节点是接收方都不递减，所以 h 跳路径的最小初始 TTL 是 h；有测试断言"h 跳恰好需要 TTL=h，h-1 就超时"。
- **等价路径怎么选？** 目前只保留一条（Dijkstra 取一条最短路径树），等价多路径（ECMP）与多下一跳是下一步工作。
- **两个节点同时故障会怎样？** 每次注入都会触发一次全网重算，注入操作加锁串行；实测 5 客户端并发注入 5 个不同节点，5 次重算共 235 ms，最慢单次 12.25 ms，指标仍满足。
- **网络分区了怎么办？** 不可达的目的地不会留在路由表里（无过期路由），分组在源节点就被丢弃并给出原因；有分区场景的测试。
- **IPv6 是"顺便支持"还是真的实现了？** 节点/链路同时分配 v4/v6 地址，路由计算为同一目的安装 v4/v6 两条路由（度量相同），转发按地址族选协议与源地址；全网 2800 条 v6 路由，实测 R2→R41 五跳送达。

### 指标与验证类（最容易追问）
- **2 秒这个指标你怎么证的？** 穷举 50 个单节点 + 75 条单链路故障共 125 个样本，最慢 13.97 ms、平均 11.4 ms；口径是纯路由重计算，另有含推送的 total_ms（23.43 ms）。不是抽样。
- **你怎么知道路由算对了？** 测试里独立实现了一份 Dijkstra 与 BFS，把系统生成的 4900 条路由与独立结果逐条比对；再加无黑洞/无过期/完备性三条不变量；端到端还校验路径代价等于独立最短路。
- **为什么优化前后能比？** 用 `git worktree` 检出改动前版本，同一测量脚本、同一随机种子、各重复 3 次取平均，排除拓扑与测量方式的差异。
- **性能瓶颈在哪？** 改动前主要在 Dijkstra 的线性选点与前缀重复解析；改动后瓶颈转移到大拓扑下的路由表构造与内存（300→400 节点增速明显），下一步是增量 SPF。

### 工程与协作类
- **Git 怎么用的？** 功能分支开发 → 合并（`--no-ff`）→ 打标签（v0.1.0~v0.4.0）；提交信息写清"为什么改"（例如"状态单一真相：接口改为派生量"），可以现场 `git log` 展示。
- **代码行数怎么统计的？** 文件总行数口径，后端 2751、测试 1149、前端 977，合计 4877（`report/scripts/measure_metrics.py` 可复现）。
- **报告里的数字和代码会不会对不上？** 报告的所有图表与数字都由脚本从实跑指标生成（measure → metrics.json → 图 → docx），不手写。

### 陷阱题（重点准备）
- **"你的 OSPF 是真的吗？"** 不是协议级实现：我实现的是它的核心机制（LSA、洪泛、LSDB、Dijkstra、序列号），没有报文格式、定时器与区域。所以我的毫秒级收敛是算法与实现效率，不能拿去和真实网络的收敛时间比较——这一点在报告里写明了。
- **"400 节点 832 ms，那 1000 节点呢？"** 没测过。按当前复杂度外推会接近或超过 2 秒，需要改增量 SPF + Trie 查找；我不会声称它能扛 1000 节点。
- **"你的模拟器会不会骗人？"** 会，而且我们抓到过：修复前节点恢复会无条件把接口置 up，导致报文穿越已断链路仍报 delivered。修法是接口状态改为派生量 + 每跳校验链路，并把该场景做成回归测试。这也是我做"不变量检查"的动机。
- **"多客户端共享一个模拟器，A 注入故障会影响 B 吗？"** 会：拓扑是全局共享的，这是教学演示的简化；并发注入已用锁串行化（同一故障只生效一次），但会话隔离与权限是待做项。
- **"为什么带宽字段没有用到？"** 它目前只是拓扑属性，没有做队列与拥塞模型；本项目聚焦路由与转发控制逻辑，不建模流量。
