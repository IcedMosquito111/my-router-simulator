# 1 研究背景和意义

## 1.1 背景

IPv4 分组转发与路由选择是《计算机网络》课程的核心内容：路由器依据路由表对分组做最长前缀匹配，逐跳转发至目的主机；当网络出现节点或链路故障时，路由协议需要重新计算并收敛到新的可用路径。这些机制在课堂上多以"路由表 + 算法伪代码"的形式讲授，学生往往难以建立直观认识：

- 路由表如何生成、如何随拓扑变化更新，缺乏可见的中间过程；
- "逐跳转发"是动态过程，静态截图无法体现；
- 路由收敛是网络可靠性的关键指标，但在真实网络中无法随意断开链路来做实验。

网络仿真因此成为理解路由机制的重要手段。但现有仿真/教学工具（Packet Tracer、GNS3、NS-3、Mininet 等）多为重量级环境：需要安装虚拟机镜像、依赖 Linux 内核特性或编写 C++ 模块，部署成本高；且其关注点通常是"网络能否连通"，对"路由收敛耗时"这类指标的定量测量支持有限。

## 1.2 意义

本项目实现一个**轻量、可交互、可度量、可复现**的 IPv4 分组转发与路由选择模拟系统，其意义体现在：

1. **把抽象机制可视化**：在浏览器中实时看到拓扑、路由表、逐跳转发动画，以及节点/链路故障后的路径变化（实测同一对端点 R1→R2 的路径由 1 跳变为 8 跳绕行）；
2. **把性能指标可度量**：提供指标接口与测量脚本，直接给出"故障后路由重新计算耗时"的分布（实测最慢 13.97 ms），而不是笼统宣称"很快"；
3. **把实验可复现**：拓扑由固定随机种子生成并可导出为 JSON，同一实验可反复重现，便于对比与验证；
4. **覆盖完整工程链路**：需求分析、协议算法实现、B/S 全栈开发、性能优化、自动化测试与版本管理，符合课程设计"综合训练"的定位。

# 2 研究历史和现状

## 2.1 路由算法的发展

- **距离向量算法**：源于 ARPANET 早期实践，1988 年标准化的 RIP（RFC 1058）以跳数为度量（最大 15 跳，16 表示不可达），实现简单但收敛慢，且存在计数到无穷问题；
- **链路状态算法**：1979 年提出，OSPF（RFC 2328）以链路代价为度量，各路由器通过 LSA 洪泛获得全网一致链路状态数据库（LSDB），再各自运行 Dijkstra 算法计算最短路径树。由于每个路由器拥有全局拓扑视图，OSPF 在拓扑变化后收敛更快，成为大型网络的主流域内路由协议；
- **转发技术演进**：1993 年 CIDR 引入无类别地址与路由聚合，使最长前缀匹配成为转发核心；此后转发平面硬件化，实现线速转发。

## 2.2 仿真与教学工具的现状

| 工具 | 典型实现方式 | 主要特点 | 用于本类实验的不足 |
| --- | --- | --- | --- |
| Cisco Packet Tracer | 专有教学模拟器 | 图形化拖拽、配置命令贴近真实设备 | 协议实现为黑盒，难以定量测量收敛时间，无法自定义算法 |
| GNS3 | 虚拟机/真实镜像 + Dynamips | 可运行真实路由软件，接近真实环境 | 部署重、依赖镜像，启动慢，不适合课堂快速演示 |
| NS-3 | 离散事件仿真框架（C++/Python） | 模型精细，可做协议级研究 | 学习曲线陡，可视化弱，开发成本高 |
| Mininet | Linux 命名空间 + 真实协议栈 | 逼近真实，SDN 研究常用 | 依赖 Linux/root，侧重拓扑与流量而非路由收敛过程 |
| FRRouting/Quagga | 真实路由协议软件 | 协议实现完整 | 需多实例部署与网络配置，聚焦协议本身而非教学演示 |

可以看出，上述工具都在"更接近真实"的方向上做了大量工作，但面向**课堂演示 + 指标可度量 + 实验结果可复现**这一组合需求时，仍存在部署重、观测难、不便交互等问题。本项目采用"轻量实现 + 浏览器可视化 + 指标接口 + 自动化测试"的路线，作为上述工具的补充。

## 6.2 关键功能模块实现

### 6.2.1 拓扑与"状态单一真相"

节点状态、链路状态、接口状态三者必须自洽。本项目的设计是：**接口状态为派生量**——接口 up 当且仅当链路 up 且两端节点都 up；任何故障注入/恢复、拓扑增删之后统一刷新：

```python
for link in self.links:
    status = "up" if self.is_link_operational(link) else "down"
    for node_id, intf_name in ((link.source_id, link.source_interface),
                               (link.target_id, link.target_interface)):
        ...  # 按名称定位接口并设置派生状态
```

这样做的直接收益是：路由表中不会出现指向"已断链路"的路由，LSA 也不会错误通告不可用邻居。对外快照中，`status` 表示链路的**有效状态**（能否承载流量），`admin_status` 保留链路自身状态，避免前端出现"节点故障但链路显示正常"的矛盾画面。

### 6.2.2 OSPF 路由计算

每次路由计算（初始化与拓扑变化后）执行三步：

1. **LSA 生成**：每个 up 节点生成本节点的 LSA（仅包含状态为 up 的邻居及其代价），并写入自己的 LSDB；
2. **LSA 洪泛**：把每个节点的 LSA 复制到其它 up 节点的 LSDB（序列号更大者覆盖旧记录）；
3. **路由计算**：每个 up 节点基于 LSDB 运行 Dijkstra，得到到其它各节点的最短路径，目的前缀取目的节点的回环地址（IPv4 `/32`、IPv6 `/128`），下一跳为出接口对端地址。

### 6.2.3 路由查找与分组转发

转发流程见下图，核心是"每一步都能解释丢包原因"：

[[FIG:fig4_forwarding_flow.png|图 6-2 分组逐跳转发流程]]

- **最长前缀匹配**：路由表项在写入时即编译为前缀对象并缓存，查找时按"同地址族 + 前缀更长者胜"选取；
- **三类下一跳**：`local`（目的地址属于本机 → 本地投递）、`direct`（直连网段 → 从出接口直接发往对端）、远端地址（按下一跳转发，并校验下一跳位于出接口网段内）；
- **可用性校验**：每一跳都检查出接口、对端节点、链路是否可用，故障链路上的分组会被明确丢弃而不是"穿过去"；
- **TTL 语义**：报文到达中转路由器时递减，减到 0 丢弃；源节点是发送方、目的节点是接收方，二者都不递减，因此 h 跳路径的最小可用初始 TTL 为 h；
- **结果可解释**：丢弃时记录原因（无路由/链路故障/TTL 超时/下一跳不在网段内），并保留已走过的路径供前端展示。

### 6.2.4 故障注入与收敛度量

故障注入流程为：设置故障（节点 down 或链路 down）→ 统一刷新接口派生状态 → 广播拓扑快照 → 触发全网路由重计算 → 推送各节点路由表 → 记录耗时指标。为避免多客户端并发注入造成状态交错，故障操作使用 `asyncio.Lock` 串行化。

度量口径明确区分为两个指标，避免"看起来很快但说不清快在哪"：

[[FIG:fig5_convergence_timeline.png|图 6-3 路由重计算耗时度量口径]]

- `convergence_ms`：**路由重新计算本身**的耗时（需求"不超过 2 秒"的判定口径）；
- `total_ms`：计算 + 向所有在线客户端推送全部路由表的耗时（端到端体验口径）。

### 6.2.5 WebSocket 服务与前端可视化

消息类型如下表：

| 方向 | 类型 | 说明 |
| --- | --- | --- |
| 服务端→客户端 | `topology_snapshot` / `topology_update` | 连接时快照与拓扑变化 |
| 服务端→客户端 | `routing_table_update` | 单节点路由表（一次故障会推送 N-1~N 条） |
| 服务端→客户端 | `log` / `packet_forwarded` | 运行日志 / 转发结果（path、ttl、status、drop_reason） |
| 客户端→服务端 | `command_response`（响应） | 命令执行结果 |
| 客户端→服务端 | `get_topology`、`get_routing_table`、`send_packet`、`inject_fault`、`recover_fault` | 五类命令 |

实现要点：广播时 JSON 只序列化一次、并发发送（`asyncio.gather`）而非串行等待，单连接超时只剔除该连接；前端在收到 `packet_forwarded` 后按真实 `path` 逐跳播放动画，并同步更新路由表面板与日志（路由表更新日志按 300 ms 聚合，避免一次故障刷屏数百行）。

### 6.2.6 双栈 IPv6 支持（提升项）

节点同时拥有 IPv4 与 IPv6 回环地址（`10.255.x.y/32` 与 `2001:db8:ffff::x/128`），每条链路同时分配 `/30`（IPv4）与 `/127`（IPv6）网段；路由计算为同一目的节点同时安装 IPv4 与 IPv6 路由（度量值相同）；转发时按目的地址的地址族选择协议与源地址。前端提供协议选择器与"目的地址"输入框。

### 6.2.7 可观测性与自动化测试

- `/api/metrics` 输出最近/最大/平均收敛耗时、故障次数、分组收发统计，并直接给出指标是否满足的判定；
- 73 项自动化测试覆盖：路由正确性（与独立 Dijkstra/BFS 交叉验证 4900 条路由）、状态一致性（故障后不"复活"死链路、报文不穿越死链路、网络分区行为）、转发语义（本机/直连投递、路径最优无环、TTL 语义、丢弃原因、IPv6）、输入校验（34 项非法输入）、性能指标（穷举单点故障断言 < 2 s）、端到端集成（真实 uvicorn + WebSocket）。

## 7.3 评价方法

**（1）指标口径与计算方法**

- `convergence_ms = (t_after - t_before) × 1000`，其中 `t_before/t_after` 由 `time.perf_counter()` 在路由重计算前后采样，仅包含算法耗时（图中红色区间）；
- `total_ms` 额外包含向所有客户端推送 N 张路由表的耗时（蓝色区间）；
- 端到端时延：由 WebSocket 客户端记录"发送故障注入命令 → 收到响应"的墙钟时间。

**（2）正确性评价方法**

- **交叉验证**：在测试中独立实现一份 Dijkstra（代价最短）与 BFS（跳数最短），把被测系统生成的每条路由与独立实现的最短路结果逐条比对；对 50 节点全网，共比对 4900 条协议路由（2450 个节点对 × IPv4/IPv6 各一条）；
- **不变量检查**：① 无黑洞路由（每条路由的出接口/链路/对端节点都可用）；② 无过期路由（不可达目的地不出现在路由表中）；③ 路由完备性（每个节点都能到达所有其它可达节点）；
- **端到端转发验证**：随机节点对发送分组，校验送达状态、路径连续、路径代价等于独立 Dijkstra 的最短路代价，且不出现环路。

**（3）健壮性评价方法**：构造 34 类非法输入（数字型 IP、非对象参数、超长节点 ID、未知命令、协议与地址版本不一致等），要求全部返回结构化错误、无副作用，且 WebSocket 连接保持可用。

## 7.5 实验结果和结论

### 收敛时间：穷举全部单点故障

| 故障类型 | 样本数 | 最慢 | 平均 | 中位数 | P95 | 与 2 秒上限的余量 |
| --- | --- | --- | --- | --- | --- | --- |
| 单节点故障 | 50 | 13.90 ms（R45） | 11.35 ms | 11.45 ms | 12.94 ms | ≥ 143 倍 |
| 单链路故障 | 75 | 13.97 ms（R3–R28） | 11.37 ms | 11.16 ms | 12.70 ms | ≥ 143 倍 |

[[FIG:fig6_fault_distribution.png|图 7-6 穷举 125 个单点故障样本的重计算耗时（对数刻度体现余量）]]

结论：**在 50 节点规模下，任意单个节点或链路故障后的路由重计算时间最慢 13.97 ms，远小于 2 秒指标**。注意本实验是**穷举**（50 + 75 = 125 个样本全部实测），而不是抽样估计，因此"任意单点故障均满足指标"是可证的事实。

### 规模扩展性与优化前后对比

| 节点数 | 链路数 | 改动前重计算耗时 | 改动后重计算耗时 | 加速比 |
| --- | --- | --- | --- | --- |
| 50 | 75 | 14.2 ms | 11.1 ms | 1.28× |
| 60 | 90 | 22.4 ms | 16.7 ms | 1.34× |
| 100 | 150 | 72.4 ms | 47.4 ms | 1.53× |
| 150 | 225 | 184.9 ms | 112.0 ms | 1.65× |
| 300 | 450 | 1103.0 ms | 446.0 ms | 2.47× |
| 400 | 600 | 2321.6 ms | 832.4 ms | 2.79× |

（改动前 = 仓库早期版本（标签 v0.1.0 之前），改动后 = 当前版本；测量使用同一脚本、同一随机种子、各重复 3 次取平均。）

[[FIG:fig7_scaling.png|图 7-7 规模扩展性与优化前后对比（对数刻度，含 2 秒指标线）]]

结论：① 50 节点规模下两种实现都远低于 2 秒，说明需求本身留有余量；② 但随着规模增大，改动前实现在 **400 节点时达到 2321.6 ms，首次突破 2 秒指标**，而改动后为 832.4 ms（仍有 2.4 倍余量），说明优化（最小堆 Dijkstra + 前缀解析缓存）显著拓宽了可用规模；③ 加速比随规模增大而提高（1.28× → 2.79×），符合"降低算法复杂度"的预期。

### 同一对端点的故障前后路径对比

| 阶段 | 路径 | 跳数 |
| --- | --- | --- |
| 故障前 | R1 → R2 | 1 |
| 链路 R1–R2 故障后 | R1 → R50 → R23 → R10 → R42 → R5 → R4 → R3 → R2 | 8 |
| 节点 R1 故障再恢复后 | R1 → R50 → R23 → R10 → R42 → R5 → R4 → R3 → R2 | 8 |
| 链路 R1–R2 恢复后 | R1 → R2 | 1 |

[[FIG:fig2_path_compare.png|图 7-8 故障前后路径对比（绿色为故障前 1 跳直连，橙色为故障后 8 跳绕行）]]

结论：故障后路由自动绕行且**不穿越已断链路**（测试同时断言路径中每条链路的有效性）；链路恢复后路由回到最优路径，说明重计算对"恢复"同样正确响应。

### 端到端时延与推送规模

| 项目 | 实测值 |
| --- | --- |
| 推送的路由表数量 | 49 张（50 节点中故障节点不推送） |
| 路由重计算耗时（convergence_ms） | 10.93 ms |
| 含推送总耗时（total_ms） | 23.43 ms |
| 客户端观测墙钟时间 | 24.4 ms |

结论：即使把 49 张路由表推送给客户端，端到端耗时仍在 **25 ms 量级**，相对 2 秒指标有约 80 倍余量；`/api/metrics` 给出的"指标满足"判定与实测一致。

### 正确性与健壮性验证

| 验证项 | 方法 | 结果 |
| --- | --- | --- |
| OSPF 路由正确性 | 与独立 Dijkstra 逐条比对 4900 条路由（IPv4 + IPv6 各 2450 条） | 全部一致 |
| RIP 算法正确性 | 与独立 BFS 跳数比对 | 全部一致 |
| 路由不变量 | 无黑洞、无过期路由、路由完备性 | 通过（故障前后均检查） |
| 端到端转发 | 随机节点对（20 组）：送达率、路径无环、代价最优、TTL 消耗 | 20/20 通过 |
| 输入健壮性 | 34 类非法输入 | 全部返回结构化错误、连接不断开、无副作用 |
| 自动化测试 | 73 项用例 | 全部通过（11.5 s） |

### 结果分析与讨论

1. **为什么能做到毫秒级收敛**：本实现的"收敛"是同步完成的算法过程（LSA 全量生成 → 洪泛 → 各节点 Dijkstra），不含真实协议的定时器等待（如 OSPF 的 Hello/Dead 间隔、SPF 延迟）。因此实测值反映的是**算法与实现效率**，而非真实网络的协议收敛时间，二者不可直接比较——报告中对此明确说明，避免夸大。
2. **性能瓶颈的定位**：优化前的主要开销不在 Dijkstra 本体的邻接遍历，而在"线性选点"（O(N²) 每次）与"每次写入路由表都重新解析前缀字符串"；改为最小堆 + 全局前缀缓存后，400 节点耗时下降约 64%。
3. **指标余量的意义**：最坏样本 13.97 ms 相对 2000 ms 有 143 倍余量，说明系统不是"卡着指标线"实现的，在节点数增长到数百时仍有可用空间。
4. **局限**：① 未模拟协议报文时序与定时器，不能用于协议行为研究；② 逐跳转发使用真实 `asyncio.sleep` 模拟链路时延，超长路径会占用命令处理时间（后续可改为虚拟时钟）；③ 单例模拟器为多客户端共享，无会话隔离与鉴权。

| 1 | 链路故障 + 节点故障/恢复后，报文"穿过"已断链路仍报告送达（仿真失真） | 节点恢复时无条件把所有接口置 up；转发时只校验节点不校验链路 | 接口状态改为派生量并统一刷新；转发每跳校验出接口/对端/链路 | `test_recovering_node_does_not_resurrect_failed_link` 等 |
| 2 | 节点故障后，相连链路在界面仍显示正常，出现"红节点 + 正常链路" | 快照直接输出链路自身状态，未反映两端节点状态 | 快照输出链路**有效状态**，另设 `admin_status` 保留自身状态 | `test_node_fault_marks_attached_links_and_interfaces_down` |
| 3 | 发送非法命令（如 `dst_ip` 传数字）会导致 WebSocket 连接被断开 | 校验缺失，异常穿透到连接处理层 | 接入 pydantic 校验，非法输入只返回错误响应；命令处理外层兜底 | `test_command_validation.py`（34 项） |
| 4 | ping 自己的回环地址、ping 直连邻居的接口地址都被丢弃 | 未处理"本地投递"与"直连投递"两类下一跳 | 增加 `local`/`direct` 路由与对应转发分支 | `test_forwarding.py`（本机/直连投递） |
| 5 | 400 节点重计算超过 2 秒（2321.6 ms） | Dijkstra 线性选点 O(N²) + 每次重新解析前缀字符串 | 最小堆 Dijkstra + 前缀解析缓存（400 节点降至 832.4 ms） | 规模实验（50~400 节点）+ 穷举故障指标断言 |
| 6 | 日志写"共 2 跳"而界面显示 1 跳 | 误把路径节点数当作跳数 | 统一按"链路数 = 节点数 − 1"计算并加断言 | `test_forwarding.py` 跳数断言 |

## 8.3 提升建议与展望

1. **协议对比教学**：把已实现的 RIP 接入前端，做 OSPF/RIP 在同一故障场景下的收敛过程对比（RIP 需补充水平分割、路由毒化、抑制计时器等机制）；
2. **洪泛过程可视化**：当前 LSA 洪泛为同步全网广播，可细化为逐跳传播动画与收敛过程时间线，更直观地展示"路由交换"过程；
3. **虚拟时钟**：用可配置倍速的虚拟时间替代真实 `asyncio.sleep`，支持长路径快速演示与大流量场景；
4. **多用户会话隔离**：为每个连接维护独立模拟实例或只读视图，并对故障注入限流，避免多客户端互相影响；
5. **工程化完善**：前端本地化 vis-network（支持离线演示）、拆分模块并引入构建、接入 CI 自动运行 73 项测试、补充登录鉴权；
6. **更大规模与真实拓扑**：加载真实骨干网拓扑（如公开的 50~200 节点拓扑数据）验证算法在多路径、非均匀代价下的表现。
